# Authentication — tranzit-route-service

This service authenticates **two classes of caller on two separate listeners**:

| Caller | Listener | Transport | Auth mechanism |
|---|---|---|---|
| End users (the mobile app) | public, behind Tailscale **Funnel** (`:8080` ← `:443`) | plain HTTP (Funnel terminates TLS) | **Supabase JWT** (`Authorization: Bearer` or `?token=`) |
| Sibling service (route-save) | **mTLS** listener (`MTLS_LISTEN_ADDR`, tailnet-only) | mutual TLS | **client certificate** issued by the private CA |

It is also itself an mTLS **client**: it calls tranzit-db-middleware (a live
`vehicle_positions` lookup during OTP route enrichment).

> **Known gap:** this service also calls **tranzit-otp** (`OTP_BASE_URL`), the
> upstream OpenTripPlanner. OTP is third-party and can't verify Supabase JWTs, so
> that hop is **not** authenticated. It is reachable only over the tailnet (plus
> whatever Funnel exposure OTP's own deploy has). If OTP is Funnel-published, drop
> that or front it with the same mTLS — see the unwrapped-services note in the
> rollout plan.

Why two listeners: Tailscale Funnel terminates TLS itself and strips any client
certificate, so X.509 mTLS can't ride the public port. The mTLS listener is a second
port bound inside the shared Tailscale netns; reachable at the node's tailnet IP but
**not** Funnel-published. The framework is Fiber, so the two listeners are two
`*fiber.App`s sharing the same route registration (`registerRoutes`) and the global
quota tracker.

Code: `auth.go` (JWT verifier + `fiberAuth` middleware), `mtls.go` (server + client
TLS, outbound `middlewareCall`), `main.go` (`registerRoutes`, `startMTLSListener`),
`otp.go` (`fetchVehicleIDByTrip` uses the mTLS client).

## Rollout — `AUTH_ENFORCE` (soft → hard)

Default is **soft** (`AUTH_ENFORCE=false`): the JWT is verified and the result
logged, but requests pass through; the mTLS listener uses `VerifyClientCertIfGiven`.
Flip to **hard** (`AUTH_ENFORCE=true`, redeploy) once logs are clean: missing/invalid
JWT → `401` (except the open paths); mTLS → `RequireAndVerifyClientCert`.

Open paths (no JWT): `GET /` (landing) and `GET /limits` (quota). Protected:
`/search`, `/details`, `/autocomplete/json`, `/route`, `/route/otp`, `/searchnearby`.

## End-user JWT (public listener)

Supabase signs access tokens with **asymmetric ES256**; verified against the project
JWKS (`{SUPABASE_URL}/auth/v1/.well-known/jwks.json`) via `golang-jwt/jwt/v5` +
`MicahParks/keyfunc/v3` (auto-refreshing → key rotation needs no redeploy). Claims:
`iss` = `{SUPABASE_URL}/auth/v1`, `aud` = `authenticated`, `exp`. Identity = `sub`.
Guests (anonymous sign-in) carry a valid token and authenticate normally. This
service has no per-user state, so authentication just gates access — there is no
ownership concept here.

## Service-to-service mTLS

A single private CA signs one leaf per service (CN/SAN = service name, `serverAuth` +
`clientAuth` EKU). As a **server**, this service verifies the caller's cert against
the CA and pins the CN/SAN against `MTLS_ALLOWED_CLIENTS` (`tranzit-route-save`). As a
**client** calling middleware, it presents its own leaf and verifies middleware's
cert against the CA with `ServerName=tranzit-db-middleware` (a SAN on middleware's
cert), so the dial can target a bare tailnet IP without an IP-SAN.

The CA + certs are generated by the **middleware** repo's `scripts/gen-mtls-certs.sh`;
copy `ca.crt` + this service's leaf (`tranzit-route-service.crt/.key`) into `certs/`
(git-ignored, mounted `./certs:/certs:ro`). Rotate by regenerating + redeploying.

### Outbound to middleware — Funnel fallback

`middlewareCall()` (mtls.go) returns an mTLS client + `https://$MIDDLEWARE_MTLS_ADDR`
when `MIDDLEWARE_MTLS_ADDR` is set; otherwise it falls back to the Funnel URL with the
default client. So you can deploy this change first and switch to mTLS by setting the
env var once middleware's mTLS listener is up.

## Environment

| Var | Purpose |
|---|---|
| `SUPABASE_URL` | Supabase project URL for JWKS verification (required when enforcing) |
| `AUTH_ENFORCE` | `false` (soft, default) / `true` (hard) |
| `MTLS_LISTEN_ADDR` | mTLS server listener, e.g. `:8443` (unset disables it) |
| `MTLS_CA_CERT` / `MTLS_CERT` / `MTLS_KEY` | CA + this service's leaf (container paths) |
| `MTLS_ALLOWED_CLIENTS` | client CNs allowed over mTLS (`tranzit-route-save`) |
| `MIDDLEWARE_MTLS_ADDR` | middleware's tailnet mTLS `host:port`; empty → Funnel fallback |
| `MIDDLEWARE_MTLS_SERVERNAME` | SAN to verify on middleware's cert (default `tranzit-db-middleware`) |

## Verify

```bash
curl -i $FUNNEL/                                   # 200 (open)
curl -i $FUNNEL/route -X POST -d '{}'              # 401 when enforced, no token
curl -i -H "Authorization: Bearer $JWT" "$FUNNEL/searchnearby?lat=51&lng=-114"

# mTLS server (over the tailnet, as route-save):
curl --cacert certs/ca.crt --cert certs/tranzit-route-save.crt --key certs/tranzit-route-save.key \
     -X POST "https://<tailnet-ip>:8443/route/otp" -d '{...}'
```
